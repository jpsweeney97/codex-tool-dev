# Implementation Planning

Write an implementation plan a skilled engineer with zero context for this codebase could execute without guessing: assume they know their craft but nothing about this repo's toolset, domain, or conventions. That is the standard, and it is what makes the plan reviewable and executable. The executor that actually reads it is `execute-plan` or another executor with the repository in front of it, which runs the tasks in order and, in subagent mode, hands each task alone to an implementer that has the repo but not this conversation, the design, or the other tasks. The plan document is the deliverable; executing it belongs to that executor.

## Trigger Boundaries

- Requires settled source material: an approved design, spec, PRD, or equivalent decision. If the design is still open, say so, name `design-exploration` where available, and ask before switching.
- Tracker issue slicing is `to-issues`; observable acceptance checks are `acceptance-map`; dependency-aware sequencing of findings is `/next-steps` or `$next-steps` where available, which the user must invoke explicitly. This lane owns the executable plan document.
- Writing the plan grants no execution authority. Do not start implementing.

## Plan Standards

- Ground the plan first: read the settled source design, spec, or PRD in full — and its acceptance map when one exists (`acceptance-map` leaves an `Acceptance map:` link in the source) — and inspect the actual repo — existing file layout, conventions, and the build/test commands — so every path, pattern, and command the plan names is one you verified, not one you assumed.
- Read the source's seams. A design or shaping capsule that marks parts as the previous lane's compression, unpriced, unconfirmed, deferred, or accepted as offered has told you those parts are not settled: treat each as a gap under the rule below, never as a premise, and when a task would build on one that changes user-visible behavior or an interface, ask before writing it. A source that says only "settled" with no seam is read as if every part were accepted as offered, and the plan says so under `Planner decisions`.
- If the source design covers multiple independent subsystems, flag it and split into one plan per subsystem; each plan should yield working, verifiable software on its own. Where `design-exploration` is available, its scope check holds the tells and the cycle test for whether a split is real: read them there and apply them here rather than re-deriving them. Without it, split only when the dependencies between the parts run one way; two parts that each need the other are one plan.
- Map the file structure before tasks: which files are created or modified and each one's single responsibility. Follow existing repo patterns.
- Number the tasks and order them so each is buildable and verifiable given only the tasks before it; when a task depends on earlier work, an earlier-numbered task must satisfy that dependency. The executor runs them in document order.
- Decompose into tasks that produce self-contained, verifiable changes. Four tells that a task is still too big — a break-it-down provocation, not a size ladder: it would take more than one focused session; its acceptance criteria will not fit in three or fewer bullets; it touches two or more independent subsystems; its title needs an "and" (that is two tasks). Within tasks, bite-sized steps — one action each: write the failing test, run it and watch it fail, implement minimally, run and watch it pass, commit. Keep test-shaped steps consistent with the `tdd` skill where available. Tasks that change prose, configuration, or documents have no failing test to write: give them the check that can run (a validator, a diff, a rendered read) and do not fake the red-green shape.
- Exact file paths always. Complete code in every code step. Exact commands with expected output. Grounding verifies paths, patterns, and commands; code and expected output are predictions until they run. Where a command can run during planning, run it in a scratch copy — never on the target tree, since writing the plan grants no execution authority — and report what it produced; where it cannot, say the output is predicted. A measured output is stronger than a guessed one, and the plan should not hide the difference.
- No placeholders. "TBD", "add appropriate error handling", "write tests for the above", and "similar to Task N" are plan failures: show the actual content, and repeat it rather than cross-referencing — the implementer of a task sees that task and no other. Reference no type, function, or method that no task defines, and in a test reference nothing an earlier or the same task has not yet defined: where the toolchain compiles the whole test target (Swift under Xcode, for one), a test that names a later task's symbol fails to build, and a failing test means a failing assertion, not a failing build.
- Gaps in the source. Complete code means the plan settles details the source never decided, and the executor will build those choices exactly. Decide a gap yourself only when the choice is small, local, and easy to reverse, and list every such choice under a `Planner decisions` heading near the top of the plan, so the user can tell your calls from the source's. When a gap would change user-visible behavior or an interface, or would cross a scope line the source drew, ask the user before writing the tasks that depend on it.

## Self-Review

After drafting, check the plan against the source material yourself:

1. Coverage: every requirement maps to a task, and every check in the acceptance map, when one exists, is run by some task's verification step. List gaps and add tasks.
2. Placeholder scan for the failure patterns above; the plan's own sentence reporting the scan is not a hit.
3. Consistency: names, signatures, and types match across tasks.

Fix issues inline and move on. This is the author's own pass: it catches placeholders, drifting names, and contradictions, and it is not an independent review. The exactness above is what makes an independent review productive — `execute-plan` reads the plan critically before it starts, and the repo's readiness reviews or a plan panel (`plan-panel-loop` where available) find the defects an author cannot see in their own draft — so do not present this pass as either.

## Outside-View Pass

Self-Review checks the plan against its source material: the inside view, where every requirement maps to a task. But a decomposition that covers the spec still inherits the spec's blind spots — an inside-view plan feels complete and systematically under-scopes, because the spec and the breakdown both omit the work everyone knows but no one wrote down. This is the planning fallacy; the correction is the outside view (reference-class forecasting). After Self-Review, run it.

1. Name the reference class. What *kind* of change is this — a schema migration, an auth-provider integration, a new endpoint, a framework bump? The class, not this specific plan, carries the base rate.
2. Consult the base rate. Prefer this repo's own track record: find comparable past plans, PRs, or changes and read what they actually required; fall back to general knowledge of how that class behaves. The forcing question: *what do changes of this class reliably require that my decomposition left out?* A plan to add an auth provider, for instance, surfaces the token-refresh path, the migration of existing sessions, and the rate-limit handling that the "add OAuth login" spec never named.
3. Edit the plan in place. Add the missing tasks, widen the ones scoped too thin, and flag the steps this class reliably balloons — qualitatively; the plan stays a task list, not a schedule, so no clock estimates. The common omissions are a provocation to check against, never a checklist to complete: integration glue, data migration and backfill, config and secrets, error and retry paths, test fixtures and infrastructure, rollback, docs, observability, performance under real load. Which of these the reference class actually demands is the judgment; running the list to feel thorough is not. Whatever you add or widen holds to the same Plan Standards as the rest — exact paths, complete code, no placeholders — so the executor follows the new tasks as exactly as the original ones.

This is the reference-class completeness debias, not failure-imagination: consult what this class of work actually required, not what could newly go wrong. If you find yourself inventing novel, plan-specific failure scenarios or wanting dated tripwires, that is `premortem` (where available), a separate pass — here you fix the plan in place. And it corrects under-scoping toward the base rate, not toward gold-plating: add what the class reliably needs, not every task it might conceivably want.

Close honestly. The reference class is one you drew, and a base rate is a prior, not a guarantee — this debiases the plan, it does not certify it complete. Name the class you compared against and where the comparison came from: the past plans, PRs, or changes you read, by name, or general knowledge only when the repo had no comparable record. Say which — a comparison drawn from memory is weaker than one drawn from the record, and the plan should not hide the difference. Credit the outside view only with what it added: what grounding found before drafting or a later review added stays theirs, even though this section is written last. Do not stamp the plan comprehensive.

## Artifact And Handoff

Save the plan to `docs/plans/YYYY-MM-DD-<topic>.md` unless the user or repo convention names another location; state the path and the planner decisions, or that there were none. Open the plan with the source path or issue reference it was derived from, the acceptance map's path when one exists for that source, and the commit the repo was inspected at: that pin says what the paths and commands were verified against, not that the plan is fresh, so never make a task's proof depend on the source commit still being `HEAD` — the plan's own commits move it. Commit only per repo convention or user request. Then name the executor: `execute-plan` for in-session execution, or `to-issues` when the user wants tracker slices instead of a plan run. A push, a merge, or a pull request is not a task: landing belongs to the repository's landing lane, and `execute-plan` stops at a reviewed, committed branch. When the user wants the run to end in a PR or a merge, say so in one line at the top of the plan for the executor to settle at its Load And Review, never as a task step. The plan's authority ends where execution's record begins: once `execute-plan` runs it, corrections and divergences live in that run's record, and a plan rewritten after execution to match what was built says so at the top, as a record rather than a contract.
